## 1. 프로젝트 목표

### 단계 0 — 초기 탐색 (폐기된 방향)
- Blender 3D 모델링, 도형 인식 모델 검토 → 멘토 가이드로 **"치수 숫자 중심"으로 방향 전환**.
- 초기 합성 도면 v4 + Tesseract 파이프라인 제작. 회전/뒤집기 증강은 목적과 안 맞아 폐기.
- 폐기 코드 기록: [ARCHIVE.md](ARCHIVE.md)

### 단계 1 — 실제 도면 수준의 합성 데이터 (`create_data_v5.py`)
실제 도면 분석에서 도출한 4대 요구사항 반영:
1. 한 장에 3개 이상의 뷰 → 2×3 그리드 4~6개 도형
2. 글씨체 노이즈/분산 → 폰트 3종, 크기/굵기/기울기 랜덤
3. 숫자 외 기호(공차 ±0,1 / 끼워맞춤 H7 / 지름 Ø / 각도 / 표면기호 ▽ / 단면기호)와
   타이틀블록 — 모든 텍스트 type 태깅 (지름 기호는 원형 피처에만 = 제도 규칙 준수)
4. 지운 흔적·선 겹침·얼룩·블러·기울기 4단계 노이즈

라벨에 정답 치수 목록 저장 → 자동 채점 가능.

### 단계 2 — 측정 기반 엔진 선택
- 채점 스크립트로 Tesseract baseline 측정: recall 35.1%
- 노이즈 레벨과 recall이 무관 → **병목은 노이즈가 아니라 검출 능력**이라는 발견
- 논문 조사 (eDOCr, YOLO-OBB+Donut, MDUS, Fletcher-Kasturi 등)
- PaddleOCR 교체: 52.8% (+17.7%p). CPU 제약상 mobile 모델 채택
- 함정 기록: paddle 3.3.1 CPU oneDNN 버그 → `enable_mkldnn=False` 필수

### 단계 3 — 실제 도면 진단 → 3패스 회전-병합 (`paddle_rotate_merge.py`)
- 실패 패턴: **세로 치수 전멸** → 원본+시계90°+반시계90° 3패스, 좌표 역변환, 겹침 중복제거
- 함정 기록: PaddleOCR 내부 문서방향 자동보정이 좌표계를 뒤틀음
  → `use_doc_orientation_classify=False, use_doc_unwarping=False` 필수
- 결과: 실제 도면 세로 치수(70±0,1 / 24 / 3/8 등) 회수. 합성 recall 90.4% 달성

### 단계 4 — 영역 분리 (`region_split.py`)
- 프레임: 60%+ 장선 (HoughLinesP, 스캔 기울기 ±5° 허용 + 팽창 보강)
- 타이틀블록: 하단형(하단 25% + 우측 경계 접촉 조건) → 실패 시 우측 기둥형
- 분류: 프레임 밖/타이틀블록 안 = meta, 나머지 = drawing. 실패 시 전체 drawing 폴백
- 효과: recall 손실 0으로 precision 60.4→71.0%
- 신규 실도면 25장(변형 묶음)으로 과적합 검증 → 우측형 레이아웃 약점 노출·보완

### 단계 5 — 점선/화살표 문제와 전처리 실험 (experiments/)
사용자가 발견한 문제: 치수 점선의 낱개 대시가 전부 '1'로 오인식 (연산 낭비 + 오염).

실험 시리즈 (01~05.png 5장 고정, 비용 통제):
| 버전 | 방법 | 결과 |
|---|---|---|
| 필터 | 획-문자 휴리스틱 후처리 | 오염 제거 (138→12박스), 근본 아님 |
| clean_v1 | morphology 점선 제거 | 01 개선 / 05 숫자 손상 (`20→2`) |
| clean_v2 | + 2단계 글자 보호 | 05 부분 회복, 한계 잔존 |
| clean_v3~v4 | **Fletcher-Kasturi 공선 체인 판정** | 대각선 대응·실선 보존·화살촉 흡수 |
| union | 원본 OCR ∪ 클린 OCR | recall 손실 0 + 클린 이점 결합 |

F-K 검증 (오버레이 전수검사): 픽셀 오제거 없음 확인. 잔여 손실은 중복제거 단계에서
회전 패스의 고신뢰 오독('2')이 가로 패스의 정독('20')을 밀어내는 현상 — 병합 우선순위
변경(글자수 우선)을 시도했으나 근거 부족(사례 1건, 튜닝셋 검증)으로 **폐기, 원복**.

**F-K 최종 판정 (대표 11장 이질 스타일 검증)**: 점선 매립형 도면(01~20류)에서는
유효하나, **손그림 스캔에서 붕괴** (scanA drawing 25→5) — 절대 픽셀 파라미터
(굵기 5px)가 벡터 렌더 스타일에 과적합. `--fk`는 점선 스타일 전용 실험 기능으로
격리, 기본 파이프라인은 전처리 없음 유지.

### 단계 6 — 다각도 패스와 도메인 지식 (마무리 단계)
- **대안 조사**: HuggingFace에 도면 전용 사전학습 모델 부재 확인 (연구 활발하나
  가중치 비공개가 업계 현실). 문자 단위 검출(CRAFT) 재정의 아이디어는 eDOCr가
  이미 검증한 경로임을 확인 — 검출기 교체 실험은 "검증된 다음 후보"로 보류.
- **문자셋 실측**: PP-OCRv5 인식기 사전(18,383자)을 직접 열어 확인 —
  대문자 Ø 없음(!), 소문자 ø·⌀·±·°·▽ 있음. 추측 대신 실측으로 파서 정규화
  테이블의 근거 확보.
- **도메인 지식 문서화**: [DOMAIN.md](DOMAIN.md) — 치수 보조기호, 공차 3형식,
  끼워맞춤(H9/f7 해독법), GD&T, 선 종류, 타이틀블록 필드. 실데이터 관찰 표기와
  규격 매핑. §10에 파서 정규식 사양 포함.
- **±45° 대각 패스 추가** (`--angles 45,-45`): 사용자 제안. 대표 11장 검증 —
  **회귀 0, 240→247 (+7)**. 각도 치수(60,0° / 20°), 지시선 사선 치수(R1.00±0.10),
  기울어진 스캔 텍스트 회수. F-K와 달리 스타일 편향 없음(회전은 이미지 무손상).
  비용 ~2배라 최종 추출 전용 옵션으로 운용.

## 3.5 파이프라인 해부 — 도면 한 장이 처리되는 과정

`python paddle_rotate_merge.py 도면.png --angles 45,-45` 실행 시:

```
[입력] 도면.png (스캔/사진/CAD 출력 무관)
   │
   ├─ (선택) 전처리 --fk : F-K 공선 체인 판정으로 점선 제거
   │         ※ 점선 매립형 도면 전용. 스캔엔 사용 금지 (검증된 한계)
   │
   ├─ ① 다방향 패스 생성
   │    원본(0°) / 시계90° / 반시계90° / +45° / -45°
   │    이유: PaddleOCR은 수평 텍스트에 최적 — 도면의 세로/사선 치수는
   │          이미지를 돌려서 수평으로 만들어 읽힌다
   │
   ├─ ② 각 패스마다 PaddleOCR 실행
   │    내부 3모델: DB 검출(픽셀별 "글자잉크 확률" → 연결 덩어리 = 박스)
   │              → 방향분류기 → CRNN 인식(박스 crop → 문자열+신뢰도)
   │    출력: [폴리곤 좌표, 텍스트, 신뢰도] 목록 (회전 이미지 기준 좌표)
   │
   ├─ ③ 좌표 역변환
   │    90°는 공식, 45°는 역아핀행렬로 → 모든 박스를 원본 좌표계로 통일
   │
   ├─ ④ 선 오인식 필터
   │    '|','1','T' 단독 / 영숫자 없음 / 획문자 반복 → 폐기
   │    (점선 대시를 글자로 착각한 검출 제거)
   │
   ├─ ⑤ 중복 제거 (병합)
   │    5개 패스가 같은 텍스트를 여러 번 잡음 → 박스 겹침 60%+ 이면
   │    신뢰도 높은 것 하나만 유지
   │
   ├─ ⑥ 영역 분리 (region_split.py)
   │    HoughLinesP 장선 → 프레임 사각형 검출
   │    프레임 하단/우측의 표 → 타이틀블록 검출
   │    각 텍스트 중심점의 위치로 태깅:
   │      프레임 밖 or 표 안 = meta (부품번호·날짜·재질...)
   │      그 외              = drawing (치수 후보)
   │    검출 실패 시 전체 drawing 폴백 (텍스트 손실 없음)
   │
   └─ [출력 2종]
        <이름>_v2.json :
          { "text": "50±0,1",      ← 인식된 원문
            "score": 0.93,         ← 신뢰도
            "poly": [[x,y]×4],     ← 원본 좌표 폴리곤
            "orient": "h",         ← 어느 패스가 잡았나 (h/v_cw/v_ccw/a±45)
            "region": "drawing" }  ← 치수 후보 vs 메타
        <이름>_v2.png : 원본 위에 박스+텍스트+신뢰도 시각화
                        (색 = 패스: 빨강 h / 초록 cw / 파랑 ccw)
        <이름>_region.png : 프레임(초록)/타이틀블록(파랑)/분류(빨강·자홍)
```

이후 계획된 소비처: JSON의 drawing 텍스트 → 공차 파서(DOMAIN.md §10 사양)
→ {공칭, 상한, 하한} 구조화 → (실측값 입력 시) ±판정 → DB 적재.

### 단계 7 — 엔지니어링 루프 종료 판단과 파인튜닝 준비 착수
- **대안 재검토**: 사용자가 paddlepaddle CPU oneDNN 버그(`enable_mkldnn=False`
  워크어라운드)의 해결 여부를 재확인 지시 → GitHub 이슈 #77340 실측: PyPI
  정식 최신판(3.3.1)엔 여전히 미해결, 픽스는 미출시 개발 브랜치(3.4.x)에만
  존재. paddleocr(API 껍데기, 3.7.0 최신)와 paddlepaddle(엔진, 버그 있는 곳)의
  버전 체계가 다르다는 혼동 정리.
- **한도 판단**: 규칙·설계 기반 개선(전처리·병합·다각도)의 수확체감을 인지,
  "추가 모델 없이는 한도에 도달"이라는 자가 평가에 합의.
- **파인튜닝 준비 착수**: PaddleOCR 공식 저장소의 TIA 증강 코드
  (`augment.py`/`warp_mls.py`) 확보 및 스모크 테스트 완료 — 인식기(rec)
  파인튜닝 시 사용할 왜곡·늘림·원근 증강 확보.
- **저장소 리팩토링**: 실험 로그·중간 산출물 정리 후 `data/`(real·repr·synth)
  `pipeline/`(핵심) `legacy/`(baseline) `finetune/`(파인튜닝 준비) `weights/`
  `results/`(생성물)로 폴더 구조 확정. 이동에 따른 하드코딩 경로·크로스폴더
  import 전량 수정 및 스모크 재검증.

## 4. 협업 기록 — 역할 분담

이 프로젝트는 사람(이규석)이 방향·판단·검증 기준을 정하고, AI(Claude)가 구현·조사·
측정을 수행하는 방식으로 진행했다.

### 역할 분담표

| 영역 | 사람 (이규석) | AI (Claude) |
|---|---|---|
| 문제 정의 | 멘토 조언 해석, 목표 확정("숫자가 기준") | 해석 오류 시 수정안 제시 |
| 데이터 | 실제 도면 수집(29장), 변형 묶음 설계, 요구사항 4개 도출 | 합성 생성기 구현, 라벨 설계 |
| 기술 선택 | 최종 선택·보류 결정 (PaddleOCR 채택, 판정기 보류 등) | 후보 비교, 논문 조사, 트레이드오프 분석 |
| 구현 | — | 전체 코드 작성·디버깅 |
| 검증 | 검증 기준 요구("냉정하게", "체크 먼저"), 문제 발견 | 측정 스크립트, 정량 비교, 오버레이 검증 |
| 비용 통제 | 실험 범위 제한 지시 (5장 고정, 재실행 금지 등) | 백그라운드 실행, 캐시 활용 |

### 사용자 의사결정 타임라인 (주요 선택과 행동)

1. **방향 교정**: AI가 "도형 크기 측정" 방향으로 오해했을 때, 멘토 조언의 맥락
   ("공장에서는 숫자가 기준, 숫자와의 일치율")을 근거로 **숫자 중심 OCR로 목표를
   재정의**. 프로젝트의 뼈대가 된 결정.
2. **합성 데이터 요구사항 정의**: 실제 도면을 직접 관찰하고 4대 요구
   (다중 뷰 / 글씨 분산 / 기호·메타 구분 / 대노이즈)를 도출해 생성기 사양으로 제시.
3. **제도 규칙 준수 요구**: 생성 도면에서 Ø가 사각형 변에 붙는 오류를 지적,
   도메인 정합성 기준 제시.
4. **측정 우선 접근 채택**: 개선안 나열 대신 "B(테스트 먼저)"를 선택해
   baseline 수치(35.1%)를 확보한 뒤 개선하는 사이클을 확립.
5. **자원 제약 인식**: 갤럭시북(무 GPU) 한계를 확인 질문으로 명확히 하고,
   "학습 없는 전략"(사전학습 추론 + 규칙)에 합의.
6. **판정기 보류 판단**: ±5% 판정기는 실측 데이터가 없어 데모 설득력이 없다고
   판단, 보류하고 추출 정확도에 집중. DB도 설계만 확정하고 구현 보류.
7. **과적합 문제 제기**: "이 도면에만 통하는 과적합 아닌가?" 질문으로 규칙의
   일반화 한계를 점검하게 함 → 이후 검증 데이터 수집으로 이어짐.
8. **검증 데이터 직접 수집**: 같은 그림에 메타데이터 위치·내용만 다른 변형
   묶음(01~20) + eDOCr 논문 도면 5장을 수집 — **영역 분리 규칙의 과적합을
   실험적으로 검증할 수 있는 데이터셋을 설계**. 실제로 우측 타이틀블록 약점이
   이 데이터로 발견·보완됨.
9. **문제 발견 및 분해**: 점선 대시가 '1'로 오인식되는 문제를 결과 이미지에서
   직접 발견하고, "화살표 오인식 + 대각선 미검출"로 문제를 정확히 분해.
10. **전처리 아이디어 제시**: "점선을 직선으로 바꾸고 숫자와 겹치는 부분을
    보호하며 제거"라는 전처리 방향을 제안 — clean 실험 시리즈의 출발점.
11. **근거 요구 습관**: 새 기법 도입 전 문헌 확인 지시("인터넷에서 최선인지
    확인"), 원리 설명 요구(F-K, DB 검출 원리, OCR 내부 구조) 후 채택 결정.
12. **실험 프로토콜 설정**: 전체 재실행 비용을 인식하고 "01~05 5장 고정,
    별도 폴더에 실험 기록" 프로토콜을 지시 — 반복 개선 사이클의 비용을 통제.
13. **검증 우선 문화**: 개선을 잇기 전에 "F-K가 제대로 된 건지 체크 먼저"를
    요구 — 오버레이 전수검사로 이어져 진짜 원인(중복제거 로직)을 특정하게 됨.
14. **저장소 관리**: 불필요 산출물 삭제, 레거시 코드는 기록(ARCHIVE.md) 후
    정리하도록 지시. 파일명 영어 체계 정비(scanA/cadA 등), 무의미 데이터(3.3) 폐기.
15. **시각적 판단 우선**: "정답 라벨 없는 태스크에서 개수 비교는 안 된다"고
    지적, 모든 실험 결과를 이미지로 저장해 직접 판단하는 체계 요구 —
    F-K의 스캔 붕괴(scanA 25→5)를 이 방식으로 확정.
16. **손절 판단**: 병합 규칙 개선 시도가 "근거 없는 휴리스틱"임을 지적하고
    검증 실행 중 자원 낭비로 판단, 중단·폐기·원복 결정.
17. **대안 조사 지시 후 현행 유지 판단**: HuggingFace 도면 모델 조사와
    문자 단위 검출 재정의 검토 후, "추가 모델 도입 외에는 할 수 있는 한도까지
    했다"는 자가 평가로 엔지니어링 루프의 종료 시점을 결정.
18. **문자셋 실측 요구**: "Ø가 문자셋에 있다고?" — AI의 주장을 의심해
    사전 파일 직접 검증을 유도, 대문자 Ø 부재(추측 오류)를 확정.
19. **다각도 패스 제안 (적중)**: "여러 방향으로 확인하는 게 가장 효과적일 것"
    이라는 가설 제시 + "01~05로는 제대로 된 테스트가 안 된다"며 이질 11장
    검증을 요구 → 회귀 0 · +7 확인 후 채택. 마지막 성능 레버를 직접 발굴.
20. **도메인 지식 수집 방향 제시**: 파서 구현 전에 도면 표기법(끼워맞춤,
    기호 의미)부터 정리하자고 순서를 정함 → DOMAIN.md.
21. **버그 상태 재검증 요구**: "이미 해결된 버그 아니야?"라며 기존 워크어라운드
    (enable_mkldnn=False)의 필요성을 다시 확인시킴. 이어 "paddleocr 3.7.0 출시"
    정보로 AI의 설명(paddleocr vs paddlepaddle 버전 혼동)을 교정하는 데 기여.
22. **파인튜닝 준비 착수 결정**: 엔지니어링 루프 종료 판단 이후, 다음 단계로
    사전학습 모델 자체의 파인튜닝을 목표로 설정 — TIA 증강 코드 확보를
    스스로 진행(augment.py/warp_mls.py 도입, 테스트 스크립트 작성).
23. **저장소 리팩토링 지시**: "파일 구조를 리팩토링하는 게 먼저"라고 우선순위를
    정하고, 파인튜닝에 선행으로 필요한 코드·데이터부터 정리하도록 순서를 설계.
    본인이 먼저 실험 로그·쓰레기 산출물을 정리(폴더 리네임 포함)한 뒤 AI에게
    구조화를 넘김.

## 5. 파일 구성 (2026-07-23 리팩토링 — src/ 레이아웃)

코드(`src/`)와 데이터/산출물(`data/`,`results/`)을 분리. **모든 스크립트는 repo
루트에서 실행**하는 것을 기준으로 데이터 상대경로가 잡혀 있음
(예: `python src/datagen/gen_det_overlay.py`). 모듈 import는 스크립트 폴더 기준이라
상호 import하는 스크립트끼리는 같은 폴더에 묶여 있음.

```
├── data/           (전체 gitignore — 0장 참고)
│   ├── real/       실 라벨 도면 (train/ — PPOCRLabel 형식)
│   ├── crop_image/ 기호 crop
│   ├── generated/  합성·증강·consolidated 산출물 (재생성 가능)
│   └── synth/      create_data_v5.py 산출물
├── src/
│   ├── datagen/    합성·증강 데이터 생성기 (flat import 묶음)
│   ├── pipeline/   추론 파이프라인
│   │   └── line_detect/  선분 검출·정제·매칭·화살촉 검출
│   ├── review/     검수 UI (PyQt5) — 자동 결과를 사람이 확인/수정
│   ├── parameter/  모델 가중치 (gitignore — 직접 채워야 함)
│   ├── eval/       정량 평가·진단
│   ├── labeling/   라벨링 도구
│   └── train/      Colab 학습/테스트 노트북
├── results/        추론·진단·검수 출력 (gitignore, 매 실행 갱신)
└── *.md            문서 (루트 유지)
```

### 리팩토링 시 주의사항 (import/경로 함정 기록)
- **모든 데이터 경로는 repo 루트 기준 상대경로** 하드코딩 — 파일 이동 시 경로 문자열도 같이 수정.
- `src/eval/eval_paddle_v2.py`는 `src/pipeline/`의 `paddle_rotate_merge`·`region_split`를
  import — `sys.path.insert(0, ...pipeline)`로 명시 연결. 폴더 재배치 시 깨지기 쉬운 지점.
- `src/datagen/`의 스크립트들은 같은 폴더 `zone_utils`/`warp_mls`/`gen_line_noise_rec`를
  flat import — 그래서 datagen 묶음은 반드시 한 폴더에 유지.
- `cv2.imread`는 한글 경로(예: `바탕 화면`)를 못 읽음 — 이미지 로드는
  `cv2.imdecode(np.fromfile(path, np.uint8), ...)` 패턴 사용 (Windows 공통 함정).

## 6. 설계 결정과 근거

1. **학습 없는 전략**: GPU 없음 → 사전학습 모델 추론 + 규칙 후처리.
   "최신 기법 = 고자원"이 아니라 "학습 = 고자원, 추론 = 저자원".
2. **측정 우선**: 모든 개선은 동일 채점으로 전후 비교 (35→53→90%).
3. **규칙의 근거**: 영역 규칙은 ISO 도면 양식 관례 기반. 비표준은 안전 폴백
   (분류만 꺼지고 검출 유지). 변형 데이터로 과적합 검증 완료.
4. **전체 OCR 후 라벨링**: 영역별 개별 OCR(eDOCr식) 대신 전체 OCR 후 태깅 —
   영역 검출이 실패해도 텍스트 손실 없음, 규칙 수정 시 OCR 재실행 불필요.
5. **DB 설계안** (구현 보류): drawings/detections(raw)/dimensions(파싱)/
   inspections(판정) 4테이블. 원시-정규화 2층 분리.
