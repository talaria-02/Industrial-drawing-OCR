# 현장미러형 — 도면 치수 추출 및 제품 오차 검사

기계 도면 이미지에서 치수를 읽고, 그 치수가 가리키는 형상을 찾아, **스마트폰으로
찍은 실제 제품과 비교해 정상/주의/불량을 판정**하는 프로그램.

```
도면 이미지                            제품 사진 (스마트폰)
    │                                      │
    ├─ OCR: 치수 텍스트 (50±0,1)            ├─ 렌즈 왜곡 보정 (체커보드/ArUco)
    ├─ 선분 검출 (LSD → 중심선 복원)          ├─ ArUco 보드로 평면 보정 (호모그래피)
    ├─ 원/호 복원 (현 → 원)                  └─ px/mm 환산 확정
    ├─ 텍스트 ↔ 형상 매칭
    ├─ 교차점 분할 → 노드/구간 그래프
    └─ 측정점 확정 ────────────┐
                              ▼
                    실측 길이 vs 도면 치수 → 정상 / 주의 / 불량
```

사람이 검수·수정할 수 있어야 실무에서 쓸 수 있으므로, 자동 처리 결과를 단계별로
꺼내 편집하는 **PyQt5 검수 UI**가 중심이다. 자동화가 목표가 아니라 "사람이 고칠 수
있는 자동화"가 목표다.

## 1. 검수 UI — 7단계

`python src/review/main.py` → 도면 열기. 단계를 버튼으로 나눈 이유는 자동 결과가
틀렸을 때 **그 단계만 사람이 고칠 수 있어야** 하기 때문이다.

| 모드 | 하는 일 | 조작 |
|---|---|---|
| **텍스트** | OCR 결과 확인·수정, 카테고리 지정 | 박스 클릭 → 값 편집, 꼭짓점 드래그 |
| **선분** | 선분 추가·삭제·끝점 이동 | 빈 곳 드래그로 추가, Del로 삭제 |
| **원/호** | 원 추가·이동·반지름 조절, 부분호↔완전원 | **원을 씌우면 그 자리 조각 선분이 자동 흡수됨** (Ctrl+Z로 함께 취소) |
| **화살촉** | 치수선 화살촉 확인 | |
| **노드** | 교차점에서 선분 분할 → 그래프화 | **분할** 버튼. 상태줄에 쪼갠 수·해칭보존·생략된 컷이 나옴 |
| **매칭** | 치수 텍스트 ↔ 선분/원 연결 | **자동매칭** 버튼, 또는 텍스트 클릭 후 형상 클릭 |
| **측정** | 사진과 비교, 판정 | 아래 2장 참고 |

Ctrl+Z / Ctrl+Shift+Z로 모든 편집을 되돌릴 수 있다(스냅샷 방식).

### 자동 결과를 다시 만들려면

파이프라인 단계(점선 병합·원 흡수·짧은 선분 규칙 등)는 **자동 실행 시점에** 돌아간다.
이미 저장된 `review.json`을 불러오면 그 안의 옛 결과를 그대로 쓰므로, 새 로직을
적용하려면 도면 열기에서 "불러올까요?" → **아니오**, 또는 툴바의 **자동 재실행**을
쓴다(현재 검수 내용은 버려진다).

## 2. 사진 측정 — 순서가 중요하다

**렌즈 보정 → 평면 보정 → 측정.** 이 순서를 바꾸면 안 된다. 스마트폰 렌즈는
미세한 볼록(어안) 형태여서 프레임 가장자리의 물체가 늘어난다. 평면 보정
(호모그래피)은 **평면 원근만** 정확히 펴주고 렌즈 왜곡은 펴지 못하므로, 왜곡이
남은 상태로 호모그래피를 걸면 그 오차가 그대로 mm로 환산된다.

### (1) 렌즈 캘리브레이션 (한 번만, 카메라마다)

```bash
# 체커보드로 (정확도 우선, 권장)
python src/measure/calibrate_camera.py data/calib/<이름> --square-mm 25

# 측정용 ArUco 보드로 (인쇄물 하나로 끝내기 — 장수를 더 찍어야 함)
python src/measure/calibrate_camera.py data/calib/<이름> --aruco --marker-mm 50 --pitch-mm 150
```

체커보드는 한 장에서 코너 54점을 주지만 2×2 ArUco 보드는 16점뿐이다. 점이 적으면
왜곡계수(특히 k2, k3)가 흔들리므로 체커보드 15~20장 자리에 **25~30장**을 찍어야
한다. `--make-board`로 인쇄용 체커보드를 만들 수 있다.

### (2) ArUco 보드 인쇄

A4에 4×4_50 딕셔너리 마커 4개(ID 0~3), 한 변 **50mm**, 중심간 **150mm**.
`A4_ArUco_Board_300DPI.png`가 그 배치다.

> **인쇄물을 자로 재서 그 값을 넣어야 한다.** 프린터 배율이 3% 틀리면 모든 측정이
> 3% 틀린다. UI 측정 모드의 `마커`·`중심간` 칸이 그 값이다.

### (3) 촬영

- 마커 4개가 **모두** 프레임에 들어오게. 3개 미만이면 자세를 신뢰할 수 없다.
- 기울기는 70°까지 견딘다(호모그래피가 평면 원근을 정확히 편다).
- **높이차가 지배적인 오차다**: `오차 ≈ 길이 × 높이 / 거리`. 부품이 종이보다
  두꺼우면 그 두께만큼 확대된다. 두꺼운 부품은 멀리서 찍는 편이 낫다.

### (4) 측정과 판정

측정 모드에서 사진을 열면 px/mm가 확정된다. 도면 치수를 클릭하고 사진 위에 선을
그으면 실측값이 표로 들어간다. 끝점은 드래그로 고칠 수 있고, 놓을 때마다 근처
에지에 **서브픽셀로 스냅**된다(수직 방향 밝기 프로파일의 포물선 보간).

판정은 항상 결론을 낸다.

| 등급 | 조건 |
|---|---|
| **정상** | 편차 ≤ 공차 |
| **주의** | 공차를 조금 넘었거나(≤ 경계), 공차 안이지만 측정 불확실도가 공차보다 큼 |
| **불량** | 그 밖 |

공차의 근거는 표에 함께 나온다 — **사용자 지정 → 도면에 적힌 공차 → ISO 2768
일반공차 → 공칭 비율 가정** 순으로 쓰고, 어느 것을 썼는지 숨기지 않는다.

OCR이 공차를 못 읽는 일이 흔하므로 **공차를 직접 입력**할 수 있다(측정 대상 표시줄
오른쪽 `± __ mm`). `0`이면 자동. 이 값은 치수별로 저장되고 선을 다시 그어도 유지된다.

## 3. 처리 흐름 — 왜 이렇게 하는가

### OCR: 다방향 패스

PaddleOCR은 수평 텍스트에 최적화돼 있어 도면의 **세로 치수가 전멸**했다. 이미지를
0°/±90°/±45°로 돌려 여러 번 읽고 좌표를 역변환해 합친다. ±45°는 각도 치수와
지시선 사선 치수를 회수한다(대표 11장 검증: 회귀 0, 240→247).

### 선분: LSD가 주는 것은 "경계"다

LSD는 그래디언트 영역 성장 방식이라 **한 획의 양쪽 경계**를 각각 선분으로 낸다.
그대로 쓰면 모든 선이 두 겹이고, 위치가 획 두께의 절반만큼 어긋난다. 그래서 두
경계 사이가 잉크인지 확인해(잉크검사) 짝을 찾아 **중심선으로 병합**한다.

임계값은 도면마다 자가보정한다. 실측 획 간격은 2.42~8.93px(3.7배 차이), OCR 글자
높이는 13~35px(2.7배 차이)로 흩어져 있어 고정 픽셀값을 쓸 수가 없다.

짧은 선분은 길이로 자르지 않는다. 짝을 찾았는가, 또는 자기 중심선이 잉크 위인가로
가른다(얇은 1~2px 선은 두 경계가 블러로 뭉쳐 애초에 짝이 생기지 않는다 — 노이즈가
아니라 이미 중심선이다).

### 점선: 간격이 아니라 주기성으로 잇는다

중심선 하나가 9조각으로 남는 문제가 있었다(대시 97px, 간격 52px). 간격 상한을
올리면 될 것 같지만, 실측하면 "공선인데 안 합쳐진 쌍" 862개의 간격 중앙값이 66px —
대시 길이의 3.2배이고 작은 간격에 봉우리가 없다. 즉 상한을 올리면 **우연히 같은
직선 위에 있는 별개의 외형선까지** 합쳐진다.

점선의 구별점은 반복이다. 공선 묶음을 1차원으로 투영해 연속한 틈만 보고
(틈 ≤ 대시×1.5) ∧ (틈끼리 고름) ∧ (대시 3개 이상)일 때만 잇는다. 치수선이 숫자에
가려 끊긴 경우는 대시가 없으므로, 틈 가운데가 OCR 글자상자 안일 때 잇는다.

### 원/호: 현을 원으로 되돌린다

LSD는 원을 짧은 현 수십 개로 쪼갠다(도면당 전체 선분의 0.5~19%, 플랜지 도면은
5분의 1). 이건 노이즈가 아니라 매칭의 전제 조건이다 — ø275는 원을 가리키는데
후보 풀에 원이 없으면 엉뚱한 현에 붙는다.

현을 "끝점이 이어지고 같은 쪽으로 계속 도는" 사슬로 엮어 원을 피팅하고, 원호를
훑어 잉크 위에 있는지 확인한 것만 채택한다. 채택된 원이 덮은 자리의 선분은
**가까움 + 기울기(접선 방향)** 두 조건으로 지운다. 접선 방향은 반드시 끝점에서
재야 한다 — 현의 방향은 자기 중점에서의 접선 방향과 항상 정확히 같아서 중점에서
재면 어떤 현이든 통과한다.

지우기 전에 호의 각도구간을 조각까지 넓힌다(잔존 조각의 60%가 "원 위에 있고
기울기도 맞는데 구간 밖"이었다). 넓히는 구간마다 잉크를 확인한다 — 안 그러면
아무것도 그려지지 않은 자리에 호가 생긴다.

### 노드: 교차점 강제 분할

LSD 선분은 서로 닿지 않는다(직교 모서리에서도 1~3px 벌어진다). 수학적 교차점을
계산해 거기서 쪼개고 끝점을 끌어당기면 이후 탐색이 그래프 순회가 된다.

전부 쪼개면 해칭에서 터지므로 (a) 거의 나란한 교차는 무시하고 (b) 한 선분이 받는
분할 수에 상한을 둔다. 그리고 **조각이 클릭할 수 없을 만큼 짧아지는 분할은 하지
않는다** — 사람이 고칠 수 없으면 단계를 나눈 의미가 없다.

한 외곽선에 치수가 여러 개 걸리는 경우와 도면에 안 적힌 치수(10−3=7)는 노드/구간
그래프에서 1차 방정식으로 풀고, 모순이 있으면 보고한다.

## 4. 파일 구성

코드(`src/`)와 데이터/산출물(`data/`, `results/`)을 분리. 모듈 import는 스크립트
폴더 기준이라, 상호 import하는 스크립트끼리는 같은 폴더에 묶여 있다.

```
├── data/            (전체 gitignore — 0장 참고)
├── results/         추론·진단·검수 출력 (gitignore, 매 실행 갱신)
├── src/
│   ├── review/      검수 UI (PyQt5)
│   ├── measure/     사진 측정·캘리브레이션·판정
│   ├── pipeline/    추론 파이프라인
│   │   └── line_detect/  선분·원·그래프·매칭
│   ├── datagen/     합성·증강 데이터 생성기 (flat import 묶음)
│   ├── eval/        정량 평가·진단
│   ├── labeling/    라벨링 도구
│   ├── parameter/   모델 가중치 (gitignore — 직접 채워야 함)
│   └── train/       Colab 학습 노트북
├── ARCHIVE.md       폐기한 코드와 그 이유
├── DOMAIN.md        도면 표기법(공차·끼워맞춤·GD&T·선 종류) + 파서 사양
└── A4_ArUco_Board_300DPI.png
```

### src/review/ — 검수 UI
| 파일 | 역할 |
|---|---|
| `main.py` | 창·모드 전환·툴바. 실행 진입점 |
| `canvas.py` | 도면 캔버스(그리기·히트테스트·편집) |
| `measure_panel.py` | 사진 캔버스 + 비교 결과표 |
| `model.py` | `review.json` 데이터 모델 + 편집 연산 + 되돌리기 |
| `bootstrap.py` | 자동 파이프라인 실행(OCR → 선분 → 원 → 매칭) |

### src/measure/ — 사진 측정
| 파일 | 역할 |
|---|---|
| `calibration.py` | ArUco 마커/보드 검출, 호모그래피 보정, 불확실도 |

## 5. 실측으로 폐기한 방향 (다시 시도하지 말 것)

측정해서 효과가 없거나 해로웠던 것들. 근거를 남겨둔다.

| 시도 | 측정 결과 |
|---|---|
| **선 굵기로 선 종류 분류** | 실도면 분포가 2.2~3.0px 단봉형 — 굵기로 갈릴 정보가 없다 |
| **LSD 그래디언트 극성으로 획/여백 구분** | 획과 여백이 모두 180°. 잉크검사와 65.8%만 일치 |
| **원 피팅에 RANSAC / 절단 최소자승** | 중앙 잔차 변화 없고 p90은 악화. 사슬 안에 이상치가 없어서 쓸 데가 없다 |
| **타원 피팅으로 늘어진 호 대응** | 각도폭 게이트를 둬도 626개 사슬 중 1개만 구제. 자유도 5개를 짧은 호가 구속하지 못해 r=100의 30° 호가 축비 0.73·장축 66px로 나온다. 이 도면들의 호는 원이다(중앙 잔차 0.60px) |
| **흡수 허용치에 호 자신의 잔차 반영** | 잔존 106 → 106 (변화 없음) |
| **EDLines** | 여전히 엣지 기반이라 "경계 두 겹" 문제를 못 푼다 |
| **EDCircles** | 작은 원 회수·속도는 우수하나 `cv2.ximgproc.EdgeDrawing` 제약. 회수 격차는 자체 코드의 파라미터 문제였고 그쪽을 고쳐 해결 |
| **cv2.HoughCircles** | 도면 1장당 259~1280개 검출, 전부 오검 |
| **컨투어 원형도로 원 검출** | 글자 О·0·6을 원으로 잡는다. 텍스트 제외가 선행되지 않으면 무의미 |
| **현 길이로 원 후보 제한(max_chord)** | 반지름이 크면 현도 길다. 40px로 자르면 큰 원을 통째로 놓친다(최대 반지름 182→1041px) |
| **병합 우선순위를 글자수 우선으로** | 사례 1건·튜닝셋 검증뿐이라 근거 부족 → 원복 |
| **Fletcher-Kasturi 점선 제거를 기본 전처리로** | 점선 매립형 도면엔 유효하나 손그림 스캔에서 붕괴(25→5). 절대 픽셀 파라미터가 벡터 렌더에 과적합 → `--fk` 실험 옵션으로 격리 |
| **회전/뒤집기 증강** | 도면 OCR 목적과 안 맞음 |

## 6. 함정 기록

- **paddlepaddle 3.3.1 CPU oneDNN 버그** — `enable_mkldnn=False` 필수. GitHub
  이슈 #77340, PyPI 정식판엔 미해결(픽스는 개발 브랜치에만). `paddleocr`(API)와
  `paddlepaddle`(엔진)은 버전 체계가 다르다.
- **PaddleOCR 내부 문서방향 자동보정이 좌표계를 뒤튼다** —
  `use_doc_orientation_classify=False, use_doc_unwarping=False` 필수.
- **PP-OCRv5 인식기 사전에 대문자 Ø가 없다** — 소문자 ø·⌀·±·°·▽는 있다.
  사전 파일을 직접 열어 확인한 값이며, 파서 정규화 테이블의 근거다.
- **`src/measure/inspect.py`로 이름 짓지 말 것** — stdlib `inspect`를 가려
  scipy(`from inspect import signature`)가 깨진다. `inspection.py`로 둔다.
- **`np.ptp(arr)`** — NumPy 2에서 `arr.ptp()` 메서드가 없어졌다.
- **`warpPerspective(borderValue=255)`의 흰 여백** — 종이 영역 검출과 섞인다.
  보정 함수가 돌려주는 `valid_mask`로 걸러야 한다.
- **어두운 부품이 종이 마스크에 구멍을 뚫는다** — 외곽 컨투어를 꽉 채워야 한다.
- **`pytest` 수집이 깨진다** — `src/datagen/test_augment.py`가 import 시점에
  argparse를 돌린다. 테스트 스위트 정비는 남은 과제.

## 8. 설계 원칙

1. **고정 픽셀값 대신 자가보정.** 도면 축척이 2.7~3.7배 흩어져 있어 절대 임계값은
   반드시 어느 도면에서 깨진다. 임계값은 그 도면에서 측정해 정한다.
2. **측정 없이 채택하지 않는다.** 라벨이 없으면 내재적 지표(잉크 피복률, 중심선
   잉크율)를 만들어서라도 전후를 비교한다. 지표 자체가 틀릴 수 있으므로 합성
   데이터로 지표를 먼저 검증한다.
3. **판단 근거를 숨기지 않는다.** 공차의 출처, 흡수한 선분 수, 생략한 분할 수를
   화면에 표시한다. 조용히 좋아 보이게 만들지 않는다.
4. **사람이 고칠 수 있게 단계를 나눈다.** 자동 결과를 한 덩어리로 주면 틀렸을 때
   손댈 수가 없다. 클릭으로 집을 수 없는 크기의 산출물은 만들지 않는다.
5. **학습 없는 전략을 우선.** GPU가 없으므로 사전학습 추론 + 규칙 후처리.
   "학습 = 고자원, 추론 = 저자원"이다.
6. **폐기한 시도를 기록한다.** 5장이 이 저장소에서 가장 값진 부분이다.

개인 프로젝트이며, 구현·조사·측정에 AI(Claude)를 협업 도구로 사용했다.
